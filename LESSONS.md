# What the C# attempt taught

Bear was first built as an unpackaged WinUI 3 desktop app in C#, with Maia 2 embedded as
ONNX. That version is gone. These are the findings worth keeping, so none of them has to be
paid for twice.

## 1. Maia 2 cannot play the opening. This is not fixable.

The symptom was self-play producing `Nf3 Nf6 Ng1 Ng8` forever. The cause is upstream and
absolute: maia2 trains with `first_n_moves: 10` (`maia2/main.py`, `if i >= cfg.first_n_moves`)
and filters its own test set the same way (`maia2/dataset.py`, `data[data.move_ply > 10]`).

**Maia 2 has never seen a position before ply 10.** Asked anyway, it is confidently wrong:

| position | Maia 2 plays | probability |
| --- | --- | --- |
| `1.Nf3 Nf6` | `Ng1` | 89% |
| `1.Nf3 d5` | `Ng1` | 85% |
| `1.Nc3 Nc6` | `Nb1` | 89% |

The tell is that confidence *rises* with rating — 56% at 1000, 89% at 1500, 98% at 2100.
That is the signature of extrapolation off the training distribution, not a quirk. The
pathology fires exactly when the side to move has no pawn moves and a developed knight, and
it disappears entirely by ply 10: from a normal 10-ply book position, greedy self-play
produced the Open Ruy Lopez accurately, tactics included.

Maia 3 retains the first ten moves during training, which is why the move to Maia 3 removed
the need for an opening book rather than working around the problem.

## 2. Verifying against an artifact proves consistency, not correctness

`tools/golden.json` was generated by running the *same ONNX file* the C# loaded. The C#
then passed 3463/3463 checks against it. Every one of those checks was real, and none of
them could ever have caught a bad export — Python and C# would agree perfectly and both be
wrong.

The checks that actually settled it went outside that loop: comparing the ONNX against the
PyTorch checkpoint it came from **on real positions**, and running maia2's own batch
inference to reproduce its published ~48% move-matching accuracy.

Related: the export script's own acceptance test compared torch to ONNX on an
**all-zeros board**. A degenerate input like that can hide a broken graph. Always validate
on inputs the program will actually see.

## 3. A build that cannot compile keeps reporting yesterday's answer

`MaiaEngine.cs` was shared by source-link into the verification harness. Startup tracing was
then added to it that called `App.Trace`, which does not exist in the harness project. The
harness stopped compiling — and kept printing results from its last successful build. The
knight-shuffle evidence came from a stale binary for as long as that lasted.

Two guards, both cheap:

- **Check the exit code, never the output text.** `dotnet publish` will print
  `Bear.App -> <path>` after skipping a build following a compile error.
- **Do not let shared source depend on the host application.** Inject a hook
  (`static Action<string>? Trace`) instead of calling into it.

## 4. WinUI single-file publish deadlocks before managed code

The published single-file exe burned ~2.2s of CPU, then parked at 63 MB with all 12 threads
blocked (7 `Wait/UserRequest`, 5 `Wait/EventPairLow` — ALPC/COM waits), `MainWindowHandle`
of 0, and never exited. No window, no crash, nothing in Event Viewer.

`App`'s constructor never ran: its first statement writes a breadcrumb and no breadcrumb
appeared. `COREHOST_TRACE=1` showed hostfxr resolving and extracting everything correctly
and handing off to CoreCLR. So the hang is between CoreCLR start and managed `Main` — a COM
or bootstrapper deadlock in the Windows App SDK self-contained path.

**Both standing hypotheses were wrong**, and disproving them is worth recording:

- *Duplicate `onnxruntime.dll`* (WindowsAppSDK's Windows ML versus the NuGet package):
  false. The extraction directory holds exactly one, byte-identical to the one in the
  folder publish that works.
- *`PublishReadyToRun`*: false. Disabling it changed nothing.

The folder publish of identical code always worked. If a desktop C# build is ever revisited,
ship the folder publish and do not spend time on single-file.

## 5. Gera.Chess is not safe to share across threads

`Board.Moves()` faulted at native level — no exception, no log, process gone — when called
on the UI thread during startup. It only fired when the random colour assignment made Maia
move first, so roughly half of launches, which made it look erratic rather than reproducible.

Worse, `Board.Moves()` returned moves in a **different order in Debug than in Release**
(`Na3` versus `Nf3` from the start position). Something in that library is concurrent or
otherwise nondeterministic. python-chess has neither problem.

## 6. What was verified correct, so it need not be re-litigated

Everything in the C# Maia pipeline was proven right before the real cause was found:

- The 18-channel encoder matched maia2's `board_to_tensor` exactly, including the mirror.
- The ONNX export matched its PyTorch source to `0.00e+00` worst-case on real positions.
- The 1880-entry policy ordering was correct — a permutation is impossible at 47.9%
  move-matching accuracy.
- Rating bucketing, move mirroring, and masked argmax all matched maia2.

The lesson is not that the work was wasted; it is that a whole correct subsystem can sit
under a bug that lives somewhere else entirely, and that "verify the layer you doubt" beats
"verify the layer you built".
